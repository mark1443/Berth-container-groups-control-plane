Notes

  • The web console is not a module; it grows a screen per module in the same order.
  • apply is listed last because it is the only module that mutates the runtime. Everything before it is read-only against your hosts, which keeps the first four modules safe to ship and test against real infrastructure.
  • A group lives on one provider in v1. Cross-provider groups (a container on EC2 talking to a Fargate task) are out of scope; see Open Questions in SPEC.md.
  • Contracts between modules live in the provider module's spec, following api-and-interface-design. The public HTTP API is specified in docs/architecture.md.

Objective

Berth is an internal tool for one operator or a small team who run applications as containers on a mix of Docker hosts (EC2 instances, VPSs) and ECS clusters, and who currently manage port mappings, environment variables, and app-to-app wiring by hand.

It does five things:

  1. Sees what is running. Connect a Docker host or an ECS cluster; Berth lists every container or task with image, status, ports, and networks, and keeps that list current.
  2. Groups them. Pick workloads on one host or cluster and name the set (for example shop: web, api, db).
  3. Takes one port and does the bookkeeping. You give the group an entry port (say 8080). The entry member gets it. Internal members get no host port at all. Members you mark as exposed get a free port allocated from a per-host range. Berth tracks every allocation and refuses collisions, so you never edit a port mapping by hand again.
  4. Manages env vars and secrets. Set values per group or per member; keep them encrypted; or reference AWS SSM Parameter Store and Secrets Manager entries. Changes are applied to the running workloads.
  5. Wires the apps together. Members of a group share a private network and find each other by name; each member receives the others' addresses as SVC_<NAME>_HOST, SVC_<NAME>_PORT, and SVC_<NAME>_URL, so nothing is hardcoded.

User stories

  • As the operator, I register an EC2 host over SSH and an ECS cluster with an IAM role, and within 30 seconds I see both inventories in one screen.
  • As the operator, I create group shop with port 8080, add three containers, mark web as the entry, click Apply, and curl http://<host>:8080 reaches web; api and db are reachable only from inside the group.
  • As the operator, I change DATABASE_URL on api, click Apply, and only api is recreated with the new value; the value never appears in logs or in any API response.
  • As the operator, I try to give a second group port 8080 on the same host and get a clear PORT_IN_USE error before anything touches the host.
  • As the operator, when somebody stops a container with docker stop outside Berth, the group shows as drifted within a minute.

Non-goals for v1

  • Deploying new images (pull and run). Berth manages what is already deployed. Deploy is the first candidate for v2.
  • Kubernetes / EKS, multi-tenant accounts, role-based access control.
  • Load balancer management (ALB listeners and target groups). On ECS, Berth records the entry port and opens the security-group rule; public routing through a load balancer stays manual in v1.
  • Cross-provider groups. A group lives on one Docker host or one ECS cluster.
  • Metrics and log streaming.

Tech Stack

  • Language: TypeScript end to end (one type system for the API contract, the console, and the adapters).
  • Console: React 18 + Vite, TanStack Query, Tailwind. Served by the API process in production.
  • Control plane: Node.js 20+, Express, Zod for boundary validation, pino logging with secret redaction.
  • State: PostgreSQL via Drizzle ORM and drizzle-kit migrations. Operations and jobs are rows in Postgres; no Redis in v1.
  • Docker adapter: dockerode over SSH (ssh2) or TCP with mutual TLS. Never plain TCP.
  • AWS adapter: AWS SDK v3 — @aws-sdk/client-ecs, client-ec2, client-servicediscovery, client-ssm, client-secrets-manager, client-sts.
  • Crypto: Node crypto AES-256-GCM for credentials and secret values at rest; master key from the BERTH_MASTER_KEY secret.
  • Tests: Vitest; Supertest for HTTP; fake provider adapters for unit and integration tests.
  • Hosting (decided): runs as a Replit deployment (web service + Postgres). It reaches Docker hosts outbound over SSH and AWS over the SDK, so no agent is installed on your hosts. Hosts must accept SSH from the internet (or through a bastion) for this to work. A Docker image for self-hosting inside a VPC remains a v2 option.

Code Style

// server/services/allocation.ts
import { and, eq, ne } from "drizzle-orm";
import { db } from "../db";
import { portAllocations } from "@shared/schema";
import { ConflictError } from "../errors";

export type AllocationRequest = {
  providerId: string;
  groupId: string;
  memberId: string;
  hostPort: number;
  protocol: "TCP" | "UDP";
};

/**
 * Claims a host port for a group member.
 *
 * The claim is a single INSERT guarded by the partial unique index
 * (providerId, hostPort, protocol) WHERE state <> 'RELEASED'. We do not
 * SELECT first: two concurrent applies would both see "free" and both insert.
 * The index picks the winner; the loser gets ConflictError(PORT_IN_USE).
 */
export async function claimPort(req: AllocationRequest) {
  try {
    const [row] = await db
      .insert(portAllocations)
      .values({ ...req, state: "RESERVED" })
      .returning();
    return row;
  } catch (err) {
    if (isUniqueViolation(err)) {
      throw new ConflictError("PORT_IN_USE", `Port ${req.hostPort}/${req.protocol} is already allocated on this host`);
    }
    throw err;
  }
}

Conventions

  • camelCase for variables, fields, and query params; PascalCase for types; UPPER_SNAKE for enum values and error codes; kebab-case for files and module ids.
  • Validate with Zod in route handlers only; services receive typed, trusted input.
  • Errors are thrown as typed classes (NotFoundError, ConflictError, ValidationError, ProviderError) and translated to the single HTTP error shape in one middleware.
  • No any; unknown plus narrowing at boundaries. No commented-out code; no TODOs that could be done now.
  • Comments explain why. Gotchas (for example "containers are immutable: a port or env change requires recreate") are documented where they bite.
  • Secret values never reach a log line, an error message, or a response body. The redaction helper is applied at the logger, not at call sites.

Boundaries

Always

  • Validate at the API boundary with the Zod schemas in shared/contracts; keep the contract and implementation in the same commit.
  • Encrypt credentials and secret values before they reach Postgres; mask them in every response (valuePresent: true, never the value).
  • Run every runtime mutation as an Operation with an idempotency key and a step log; record intent before calling out.
  • Run npm run check && npm test before each commit; keep new API fields optional and additive.
  • Write or update an ADR when choosing a dependency, changing the data model, or changing provider semantics.

Ask first

  • Adding a dependency; adding Redis or any second datastore.
  • Schema changes after the first migration ships.
  • Any operation against an ECS service whose cluster is tagged env=prod, until the operator has run at least one successful apply on a non-prod cluster.
  • Load balancer, DNS, or IAM policy changes beyond the documented least-privilege policy.
  • Changing the SVC_* injection prefix or env merge rules (consumers will depend on them — Hyrum's Law).

Never

  • Commit secrets, keys, or .env files; log a secret value; return a secret value from the API.
  • Touch a container or task that is not a member of a group (no docker rm -f on unmanaged workloads).
  • Expose a Docker daemon over plain TCP, or store a Docker socket path that is not the control plane's own.
  • Remove a failing test or lower a coverage threshold to make a build pass.
  • Hard-delete an Operation or an ADR.

Success Criteria

  1. Discovery. After registering a Docker host (SSH) and an ECS cluster, GET /api/workloads lists every running container and task with image, status, and ports within 30 s, and reflects a container stopped outside Berth as MISSING within 60 s.
  2. Group + port. Creating group shop (entry port 8080) on a Docker host with members web (ENTRY, container port 3000), api (INTERNAL, 4000), db (INTERNAL, 5432), then applying, results in: curl http://<host>:8080 served by web; api and db with no host port bindings; all three attached to network berth-shop; api with SVC_DB_HOST=db, SVC_DB_PORT=5432, SVC_WEB_URL=http://web:3000 in its environment.
  3. Collision safety. A second group requesting entry port 8080 on the same host receives 409 { error: { code: "PORT_IN_USE" } } before any provider call; the partial unique index on (providerId, hostPort, protocol) enforces this under concurrency (tested with 20 parallel requests, exactly one wins).
  4. Config. Setting secret API_KEY on api and applying recreates only api; the value is absent from logs and from GET /api/groups/:id/members/:memberId/config (valuePresent: true).
  5. ECS (EC2 launch type, bridge networking). Applying a group on an ECS service registers a new task-definition revision with the environment, secrets (SSM / Secrets Manager ARNs passed through), port mappings whose host ports come from Berth's allocations, and Service Connect configuration, updates the service, and waits for it to be stable; the entry port has an ingress rule on the container instance security group.
  6. Idempotency. Re-sending POST /api/groups/:id/applies with the same Idempotency-Key returns the original operation (200, same id) and performs no second recreate; the same key with a different body returns 422 IDEMPOTENCY_KEY_REUSED.
  7. Rollback. If a recreated container fails its health check, Berth restarts the previous container and marks the operation FAILED with the step that failed; no member is left stopped.
  8. Quality gates. npm run check, npm run lint, and npm test pass; coverage targets above are met; every endpoint in shared/contracts has an integration test.

Open Questions

  1. ECS launch type. Resolved: EC2 launch type. With bridge networking Berth allocates host ports on ECS exactly as on Docker hosts. Task definitions that use awsvpc are still supported in validate-and-record mode (canChooseHostPort = false). Fargate is not targeted.
  2. Public reachability on ECS. With no load balancer management in v1, the entry port is reachable on the container instance's address (bridge mode maps it onto the EC2 host) or through whatever ALB you already have. Default until answered: ALB target-group registration stays out of v1.
  3. Service Connect. Per-group wiring on ECS uses ECS Service Connect with a Cloud Map namespace per group (supported with bridge networking on the EC2 launch type). If you already use Cloud Map or App Mesh, Berth should match it instead. Default until answered: Service Connect.
  4. Where the control plane runs. Resolved: Replit deployment. Berth reaches Docker hosts over SSH and AWS over the SDK from Replit. Each registered host needs inbound SSH from Berth's egress (a bastion or an allow-list on port 22).
  5. Auth. v1 proposes a single admin login (username + password, session cookie). Default until answered: single admin.
  6. Secret reveal. v1 never shows a stored secret value again after it is saved. Default until answered: no reveal action.
  7. Scale. Roughly how many hosts, clusters, and containers? The 30 s polling design is comfortable up to a few hundred workloads. Default until answered: polling plus Docker events.

System shape, domain model, the provider contract, port and config models, apply flow, HTTP API, security, failure modes.

Status: Accepted, v0.2 (2026-10-21). Decisions applied: ECS EC2 launch type with bridge networking; control plane hosted as a Replit deployment. Pairs with SPEC.md (what and why), CAPABILITY-MAP.md (modules and build order), and docs/decisions/ (the reasoning behind each choice below).

1. System overview

Berth is a single control-plane service with a web console, backed by Postgres. It holds desired state (groups, port allocations, config, wiring) and continuously observes actual state on two kinds of runtime through two adapters behind one interface. It never installs an agent on your hosts: Docker hosts are reached outbound over SSH (or mutual TLS), ECS through the AWS SDK.

Design rules that fall out of this shape:

  • Read before write, by construction. Modules providers, discovery, groups, config, and integration only read from runtimes or write to Postgres. Only apply mutates a runtime, and it does so through a logged, idempotent Operation.
  • One model, two runtimes. The core never sees a Docker container or an ECS task; it sees a Workload. Runtime differences are absorbed by the adapters and declared through ProviderCapabilities so the UI can grey out what a runtime cannot do (for example choosing a host port on Fargate).
  • Desired state is the source of truth, observed state is evidence. A group is "applied" when the planner finds no diff between the two. Anything else is DRIFTED, which is a state to show, not an error to hide.

3. The Provider interface (the contract between core and runtimes)

Defined first; both adapters and the in-memory fake implement it. Core code depends only on this.

export interface Provider {
  readonly kind: "DOCKER_HOST" | "ECS_CLUSTER";
  capabilities(): ProviderCapabilities;
  checkConnectivity(): Promise<ConnectivityReport>;

  // discovery (read-only)
  listWorkloads(): Promise<ObservedWorkload[]>;
  inspectWorkload(externalId: string): Promise<ObservedWorkloadDetail>;
  watch?(onEvent: (e: WorkloadEvent) => void): Promise<Unsubscribe>; // Docker events; ECS polls

  // mutation (apply only)
  ensureNetwork(group: GroupRef): Promise<NetworkRef>;
  applyMember(plan: MemberPlan): Promise<MemberResult>;   // recreate container / register task def + update service
  rollbackMember(plan: MemberPlan, previous: MemberResult): Promise<void>;
  releaseNetwork(ref: NetworkRef): Promise<void>;

  // secrets (read-only)
  resolveSecretRef?(ref: SecretRef): Promise<string>;      // SSM / Secrets Manager, used for Docker hosts only
}

export interface ProviderCapabilities {
  canChooseHostPort: boolean;        // Docker: true. ECS EC2 launch type, bridge mode: true. awsvpc task definitions (and Fargate): false
  canRecreateInPlace: boolean;       // Docker: true. ECS: false (new task-definition revision + service update)
  supportsNativeSecrets: boolean;    // ECS: true (secrets[] with ARNs). Docker: false (values injected at apply)
  supportsEvents: boolean;           // Docker events stream: true. ECS: false
  serviceDiscovery: "DOCKER_DNS" | "SERVICE_CONNECT";
}

4. Port model

You give a group one number: its entry port. Everything else is derived.

Member roleHost portWho reaches it
ENTRY (exactly one)the group's entry portthe outside world
INTERNAL (default)noneother members, by serviceName on the group network
EXPOSEDallocated from the host's range (default 20000–29999)the outside world, on a port Berth chose and recorded

Allocation rules

  1. A claim is a single INSERT into port_allocations; the partial unique index decides collisions. There is no check-then-insert.
  2. Before claiming, the allocator also consults observed state: host ports already bound by unmanaged containers on that host are treated as taken, so Berth never fights a container it does not own. These are advisory (they can change under us); the unique index is the guarantee among Berth's own groups.
  3. On ECS with the EC2 launch type and bridge networking (the operator's setup), the allocator works exactly as on Docker hosts; the per-host range applies per container instance. For awsvpc task definitions canChooseHostPort is false: the entry port must equal the entry member's container port, and the allocator validates and records instead of choosing.
  4. Allocations move RESERVED → APPLIED when the operation succeeds and → RELEASED when a member leaves or the group is deleted. Released rows are kept for audit; the partial index ignores them.
  5. Changing the entry port is an apply like any other: claim the new port first, recreate the entry member, release the old port last. A failed apply releases the new claim.

5. Config and secrets

  • Two scopes, one merge rule: MEMBER overrides GROUP by key. Injected SVC_* variables are added last and cannot be overridden (they are the wiring, not config).
  • MANUAL values are encrypted with AES-256-GCM under a per-row data key wrapped by BERTH_MASTER_KEY. Key rotation re-wraps data keys; it does not re-encrypt values.
  • AWS_SSM and AWS_SECRETS_MANAGER entries store only the reference. On ECS the reference is passed through natively in secrets[], so the plaintext never transits Berth. On Docker hosts there is no native equivalent: the adapter resolves the reference at apply time and injects the value into the container's environment. This is a known trade-off, documented as a gotcha in the UI: anyone with docker inspect on that host can read it.
  • Responses never carry secret values. A config entry reads as { key, isSecret: true, valuePresent: true, source, sourceRef?, updatedAt }.
  • Redaction is enforced at the logger (pino redact paths plus a value-based scrubber seeded with the current secret set), not at call sites.

Injected variables, for member api in group shop with members web (3000), api (4000), db (5432):

BERTH_GROUP=shop
BERTH_SELF=api
BERTH_SELF_PORT=4000
SVC_WEB_HOST=web      SVC_WEB_PORT=3000   SVC_WEB_URL=http://web:3000
SVC_DB_HOST=db        SVC_DB_PORT=5432    SVC_DB_URL=tcp://db:5432

HOST is the member's serviceName, resolvable on the group network by Docker DNS or Service Connect. The prefix and URL scheme per member are configurable at the group level; changing them after first apply is an "ask first" boundary because consumers will depend on them.

6. Apply: from desired state to runtime operations

  1. Operator clicks Apply → POST /api/groups/shop/applies with an Idempotency-Key.
  2. API inserts the operation; the unique index on (groupId, idempotencyKey) replays an existing one instead of starting a second.
  3. API claims port allocations in the same transaction; the partial unique index on (providerId, hostPort, protocol) rejects collisions with 409 PORT_IN_USE.
  4. API answers 202 { operation: PENDING }. Nothing has touched a host yet.
  5. Executor loads desired and observed state and computes plan = diff(desired, observed, capabilities) — a pure, unit-tested function.
  6. Executor → adapter: ensureNetwork(shop) (Docker user-defined network or ECS Service Connect namespace).
  7. For each member in order INTERNAL → EXPOSED → ENTRY: write the step as RUNNING before the call, then applyMember(plan). Success records the result; failure triggers rollbackMember(previous) and marks the operation FAILED at that step; a timeout leaves the step UNKNOWN for discovery to reconcile.
  8. On success: allocations → APPLIED, group → APPLIED, operation → SUCCEEDED.

Planner rules

  • The plan is a pure function of (desired, observed, capabilities) and is unit-tested as such. Steps are ENSURE_NETWORK, APPLY_MEMBER, OPEN_INGRESS, RELEASE_PORT, RELEASE_NETWORK.
  • Members are applied INTERNAL → EXPOSED → ENTRY so dependencies are up before the public face moves. Each member is one step; a step is retried at most twice on transport errors and never on provider-reported validation errors.
  • Docker recreate (the adapter's applyMember): inspect → create name.berth-next with the same image, command, mounts, restart policy, and labels, plus new Env, PortBindings, and network attachment → stop old → rename old to name.berth-prev → rename new to name → start → health probe → remove prev. On failure: stop new, rename and start prev, remove new. Anonymous volumes are flagged in the UI before apply because recreate cannot carry them.
  • ECS apply: describe service and task definition → register a new revision with updated portMappings (host ports from allocations in bridge mode), environment, secrets, Service Connect configuration → UpdateService → waitUntilServicesStable (bounded). ECS's own deployment circuit breaker performs the rollback; Berth records the outcome. In bridge mode a rolling deployment briefly needs the old and new task on the same instance, so the host port is reserved for the new task only after the old one drains; Berth uses minimumHealthyPercent = 0 / maximumPercent = 100 for single-instance services and documents this as a gotcha.
  • Every call has three outcomes, not two. A timeout leaves the step and the operation in UNKNOWN; the next discovery pass reconciles it to SUCCEEDED or FAILED from observed state. Berth never auto-retries an UNKNOWN mutation.

7. Discovery and drift

  • Docker: on connect, listContainers({ all: true }); then subscribe to the events stream (start, die, destroy, rename, network connect/disconnect) with a 30 s full poll as the safety net.
  • ECS: a 30 s poll per cluster: ListServices → DescribeServices → ListTasks → DescribeTasks, with task-definition descriptions cached by ARN.
  • Each pass upserts Workload rows and marks anything not seen for two passes as MISSING.
  • Drift detector: for each APPLIED group, compare observed ports, network membership, and envHash with desired; any difference sets the group to DRIFTED with a per-member reason. Drift is shown, not auto-corrected; "Re-apply" is one click and one operation.

9. Security

  • Secrets at rest: AES-256-GCM, data keys wrapped by BERTH_MASTER_KEY (32 bytes, provided as a deployment secret, never in the repo).
  • Docker transport: SSH with a dedicated key pair generated by Berth and shown once for authorized_keys, or mutual TLS with a client certificate. Plain tcp:// is rejected at validation.
  • AWS: least-privilege policy shipped in docs/aws-policy.json — ecs:List*, ecs:Describe*, ecs:RegisterTaskDefinition, ecs:UpdateService, ec2:DescribeSecurityGroups, ec2:AuthorizeSecurityGroupIngress, ec2:RevokeSecurityGroupIngress, servicediscovery:*Namespace* and *Service*, ssm:GetParameter(s), secretsmanager:GetSecretValue, iam:PassRole scoped to task roles, sts:GetCallerIdentity.
  • Auth: single admin account, Argon2id password hash, HTTP-only session cookie, CSRF token on mutations. OIDC is a v2 candidate.
  • Audit: every Operation and every config change records who, when, and the diff (keys only for secrets).
  • Third-party responses (Docker API, AWS) are parsed through Zod before use; unexpected shapes become PROVIDER_REJECTED, never a crash or a trust decision.

11. Risks and mitigations

  • Downtime per recreate. Each Docker member restarts once per apply (seconds). Mitigation: order INTERNAL → EXPOSED → ENTRY, apply only members whose desired state changed, show the plan before running it. Blue/green on Docker hosts is a v2 candidate.
  • Secrets visible via docker inspect on Docker hosts. Inherent to Docker environment injection; mitigated by documenting it and by preferring ECS native secrets where available. A file-mount delivery mode is a v2 candidate.
  • SSH transport stability. One pooled connection per host with keepalive and exponential backoff; discovery degrades gracefully, apply refuses to start on a DEGRADED provider.
  • Hyrum's Law on SVC_*. Once apps read these names they are a contract; they are versioned by group setting (injectionVersion: 1) and never changed in place.

4 · Decisions (ADRs)

Each expensive-to-reverse choice, with the alternatives rejected and why. Stored in docs/decisions/.

ADR-001: One Workload model over two runtimes (Docker Engine API and ECS)

Status

Accepted (2026-10-21)

Date

2026-10-21

Context

The operator runs containers on Docker hosts (EC2 instances and VPSs) and on ECS (EC2 launch type). The two runtimes have different control surfaces: Docker exposes containers and networks through the Engine API on each host; ECS exposes services, tasks, and task definitions through the AWS API, and the control plane has no socket access to ECS container instances. Groups, port bookkeeping, config, and wiring must behave the same from the operator's point of view regardless of where a workload runs.

Decision

Define a single Provider interface and a runtime-neutral Workload model in the core. Ship two adapters, docker (dockerode over SSH or mutual TLS) and ecs (AWS SDK v3), plus an in-memory fake adapter for tests. Runtime differences are declared through ProviderCapabilities (for example canChooseHostPort, supportsNativeSecrets) and consumed by the planner and the UI, rather than special-cased in core code. No agent is installed on hosts; all access is outbound from the control plane.

Alternatives Considered

Docker hosts only

  • Pros: one adapter, simpler port model, events stream everywhere
  • Cons: leaves the ECS workloads unmanaged, which is half of the operator's estate
  • Rejected: does not meet the requirement

An agent on every host (Kubernetes-style node agent)

  • Pros: local socket access, push-based discovery, no SSH management
  • Cons: one more thing to install, upgrade, and secure on every host; impossible on Fargate anyway
  • Rejected: operational burden with no benefit for ECS

Embed or wrap Portainer

  • Pros: mature Docker management UI exists today
  • Cons: no concept of groups with a single entry port, no allocation bookkeeping, ECS support is not a first-class model; the custom semantics would live outside it anyway
  • Rejected: the valuable parts of this tool are exactly what Portainer does not model

Consequences

  • Core services and the planner are testable against the fake adapter without any infrastructure.
  • Each adapter must pass the same contract test suite, which keeps behaviour aligned.
  • Capability flags push runtime limits (Fargate port rigidity) to validation time instead of apply time.
  • Adding a third runtime later (for example Kubernetes) means one adapter, not a core rewrite.

ADR-002: Entry port given by the operator, everything else allocated and recorded

Status

Accepted (2026-10-21)

Date

2026-10-21

Context

The operator wants to "just give a port" and never edit host↔container port mappings by hand. A group typically has one public-facing member and several members that only talk to each other. Port collisions on a shared host are the common failure today. The operator's ECS services use the EC2 launch type with bridge networking, where host ports are chosen in the task definition; awsvpc task definitions do not allow choosing a host port (host port equals container port).

Decision

A group has exactly one ENTRY member that receives the operator-supplied entry port. Members default to INTERNAL and get no host port at all; they are reached over the group network by name. Members marked EXPOSED get a host port allocated from a per-host range (default 20000–29999). Every allocation is a row in port_allocations with a partial unique index on (providerId, hostPort, protocol) WHERE state <> 'RELEASED'; a claim is a single INSERT and the index decides collisions. Observed ports of unmanaged containers are treated as taken when allocating. On runtimes where canChooseHostPort is false, the allocator validates and records instead of choosing.

Alternatives Considered

One reverse proxy on the given port, routing to members

  • Pros: a single public port for the whole group, path or host based routing, TLS termination in one place
  • Cons: adds a proxy container per group that Berth must also manage; changes how apps see client IPs and headers; the operator explicitly chose bookkeeping over a proxy in the clarification round
  • Rejected: not what was asked for; can be added later as an optional group feature

Operator chooses every host port manually, Berth only validates

  • Pros: trivial to implement
  • Cons: this is the current pain; collisions still happen at the moment of choice
  • Rejected: fails the objective

Check-then-insert allocation in application code

  • Pros: readable
  • Cons: two concurrent applies both read "free" and both proceed; the race is exactly the collision we are trying to prevent
  • Rejected: the unique index is the correct mechanism

Consequences

  • Most members need no host port, which reduces the host's exposed surface compared with today.
  • The allocator is a small pure core with one SQL guarantee, easy to test under concurrency.
  • Groups on awsvpc task definitions are more constrained; the UI must explain why a port field is read-only there.
  • Released allocations are kept for audit; cleanup is a retention job, not a delete on release.

ADR-003: Encrypted config in Postgres, AWS SSM and Secrets Manager as referenced sources

Status

Accepted (2026-10-21)

Date

2026-10-21

Context

Environment variables and secrets are currently scattered across env files on hosts and task definitions in AWS. The operator wants one place to manage them for Docker hosts and ECS alike. ECS supports secrets natively (secrets[].valueFrom with SSM or Secrets Manager ARNs); Docker containers only receive plain environment variables.

Decision

Store config entries per group and per member in Postgres. MANUAL values are encrypted with AES-256-GCM using per-row data keys wrapped by a master key held as a deployment secret. AWS_SSM and AWS_SECRETS_MANAGER entries store only the reference. On ECS the reference is passed through natively so the plaintext never transits Berth. On Docker hosts the adapter resolves the reference at apply time and injects the value into the container environment. Secret values are never returned by the API or written to logs; redaction is enforced in the logger.

Alternatives Considered

HashiCorp Vault (or another dedicated secret store)

  • Pros: strong audit, dynamic secrets, leasing
  • Cons: a second system to run and secure; the operator is already on AWS, which provides SSM and Secrets Manager
  • Rejected: operational weight for a small team; AWS stores cover the need

Env files managed on each host

  • Pros: no encryption in Berth
  • Cons: sprawl across hosts, no audit, nothing comparable for ECS
  • Rejected: reproduces the current problem

Plaintext in Postgres with database-level encryption only

  • Pros: simplest code
  • Cons: any read access to the database or a backup exposes every secret
  • Rejected: unacceptable blast radius

Consequences

  • Key rotation re-wraps data keys without re-encrypting values.
  • Docker-host injection makes values visible to anyone with docker inspect on that host; this is documented in the UI as a gotcha and is the reason ECS native secrets are preferred when available.
  • The least-privilege AWS policy must include ssm:GetParameter(s) and secretsmanager:GetSecretValue for Docker-host resolution, and iam:PassRole for ECS task execution roles that read secrets.

ADR-004: Per-group private network plus injected SVC_* variables

Status

Accepted (2026-10-21)

Date

2026-10-21

Context

Apps in a group need to reach each other without hardcoded addresses. Docker provides DNS by container name or alias on user-defined networks; ECS provides Service Connect (backed by Cloud Map) for the same purpose. Apps are existing containers that cannot be modified, so wiring must arrive through configuration they already read: environment variables.

Decision

Each group gets a private network: a user-defined bridge network berth-<group> on Docker hosts, or an ECS Service Connect namespace berth-<group> on ECS. Members are reachable by their serviceName. On apply, every member receives SVC_<NAME>_HOST, SVC_<NAME>_PORT, and SVC_<NAME>_URL for each other member, plus BERTH_GROUP, BERTH_SELF, and BERTH_SELF_PORT. Injected variables are added after config merge and cannot be overridden. The naming scheme is versioned per group (injectionVersion) and never changed in place.

Alternatives Considered

Consul or another service registry

  • Pros: health-aware discovery, works across hosts
  • Cons: another system to run; apps would need a client or a sidecar; cross-host groups are out of scope in v1
  • Rejected: heavier than the problem

Sidecar proxy per member (service mesh style)

  • Pros: retries, mTLS, observability for free
  • Cons: doubles the container count, needs per-runtime mesh setup, significant operational knowledge
  • Rejected for v1: revisit if cross-host groups become a requirement

Hardcoded addresses written by the operator

  • Pros: nothing to build
  • Cons: this is the manual glue the tool exists to remove
  • Rejected

Consequences

  • Internal members need no host ports at all (see ADR-002).
  • Once apps read SVC_* names they are a public contract under Hyrum's Law; changes require a new injection version and an explicit migration.
  • ECS Service Connect requires a Cloud Map namespace and the servicediscovery permissions in the AWS policy; all members of an ECS group must be in the same cluster and VPC. Service Connect supports bridge and awsvpc network modes on the EC2 launch type, not host mode.

ADR-005: TypeScript end to end, Express + Postgres, single deployable, no Redis

Status

Accepted (2026-10-21)

Date

2026-10-21

Context

The tool has a web console, an HTTP API, background discovery, and a job runner that performs long-running applies. The team is small; operational simplicity matters more than peak throughput. The control plane needs good client libraries for the Docker Engine API and for AWS.

Decision

Build everything in TypeScript: React + Vite console, Express API with Zod validation, Drizzle ORM on PostgreSQL, dockerode for Docker, AWS SDK v3 for ECS and related services. Ship as one process that serves the console, the API, and the job runner, with operations and jobs persisted in Postgres (no Redis, no external queue). Run it as a Replit deployment (decided at approval), reaching Docker hosts outbound over SSH and AWS over the SDK. A Docker image for self-hosting inside a VPC is a v2 option, not part of v1.

Alternatives Considered

Go

  • Pros: native fit for Docker tooling (the Docker client is Go), single static binary, strong concurrency
  • Cons: two languages once the React console exists; contract types would be duplicated or generated; slower iteration for a solo operator
  • Rejected: shared Zod contracts across API and console are worth more here than Go's runtime advantages

Python (FastAPI)

  • Pros: fast to write, good AWS SDK
  • Cons: weaker Docker client ecosystem for streaming events, two languages with the console
  • Rejected for the same reason as Go

Separate worker process with Redis-backed queue (BullMQ)

  • Pros: isolation of long-running applies, horizontal scaling
  • Cons: a second datastore to run and secure; the expected load (tens of hosts, hundreds of workloads) does not need it
  • Rejected for v1: the job table design allows extracting a worker later without changing semantics

Consequences

  • One npm run dev runs the whole system; tests use the fake provider and a real Postgres.
  • Long applies run inside the API process; the operation table makes them resumable after a restart.
  • Hosts must accept SSH from Berth's egress; hosts in private subnets need a bastion. If that becomes a blocker, the self-hosted image moves into scope.

ADR-006: Apply is a planned, idempotent reconcile with recorded intent

Status

Accepted (2026-10-21)

Date

2026-10-21

Context

Changing a port or an environment variable on a running container requires recreating it; on ECS it requires a new task-definition revision and a service update. These are multi-step, non-atomic operations against remote systems that can time out. Retries from the UI or from a flaky network must not recreate a container twice or leave a member stopped with no record of why.

Decision

Model every mutation as an Operation with an operator-supplied Idempotency-Key, claimed by a unique index in the same transaction that records the operation. The executor computes a plan as a pure function of desired state, observed state, and provider capabilities, then runs steps in order INTERNAL → EXPOSED → ENTRY, writing each step's intent before calling the provider. Each step has three outcomes: succeeded, failed, unknown. Failures roll back that member; unknown outcomes are never auto-retried and are reconciled by the next discovery pass. Same key with a different body is rejected (422 IDEMPOTENCY_KEY_REUSED); a concurrent apply on the same group is rejected (409 OPERATION_IN_PROGRESS). Keys are retained 30 days.

Alternatives Considered

Imperative endpoints per action (/restart, /set-env, /map-port)

  • Pros: simple to understand one at a time
  • Cons: no single place where the end state is known; partial failures leave the group in an undefined mix; retries duplicate side effects
  • Rejected

Generate a docker-compose file per group and run compose up

  • Pros: familiar, declarative on Docker hosts
  • Cons: compose does not cover ECS (the ECS compose integration is retired); compose takes ownership of containers it did not create poorly; harder to express member-level rollback
  • Rejected: would split the model by runtime, defeating ADR-001

Check for an existing operation, then act

  • Pros: no unique index needed
  • Cons: a time-of-check/time-of-use race under retry storms, which is precisely when duplicates are most expensive
  • Rejected: the unique index is the mechanism

Consequences

  • The planner is unit-testable without infrastructure and its output is shown to the operator as a dry run before any apply.
  • A crash mid-apply leaves evidence (step RUNNING or UNKNOWN) rather than a silent half-state.
  • Operators must send an idempotency key; the console generates one per apply click and reuses it on retry.
  • Operations are never hard-deleted; they are the audit trail.
